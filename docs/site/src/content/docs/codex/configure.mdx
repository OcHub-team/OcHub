Codex uses both `config.toml` and `auth.json`. The first stores models and
providers; the second stores official account login material. OcHub manages
them as one connection without pretending that an API key is an
official login.

## Choose an authentication mode

| Mode | Account state | Model-request credential | Use it for |
| --- | --- | --- | --- |
| Third-party API only | ChatGPT login not required | Third-party API key | A fully third-party Responses upstream |
| ChatGPT login only | Uses `auth.json` | Official login state | Official Codex account and endpoint |
| ChatGPT login + third-party API | Preserves `auth.json` | Third-party API key | Account features with third-party model requests |
| ChatGPT login + OcHub relay | Real login or explicit virtual login | Login token → OcHub route identity | Third-party routing with context management |

In combined mode, `auth.json` still owns the account. Model requests use the
current provider's `experimental_bearer_token`.

<Aside type="note" title="OAuth and API keys have separate jobs">

**Keep current OAuth for third parties** prevents a switch from
overwriting `auth.json`. It does not replace an API key required by a
third-party upstream.

</Aside>

## Configure a third-party Responses upstream

<Steps>

1. **Open Codex and add a connection.** Start from a preset when one matches, then
   verify every field.

2. **Set the Provider ID.** This is the key under
   `[model_providers.<id>]` and the value of `model_provider`. Use a short,
   stable identifier without spaces, such as `company_proxy`.

3. **Set the provider name.** This is an internal Codex provider name, not the
   display name of the OcHub card.

4. **Enter the Base URL.** Third-party mode normally ends in `/v1`, after which
   Codex appends `/responses`.

5. **Choose auth and enter a key.** Third-party API and combined mode use the third-party
   key. Login-only mode does not.

6. **Choose a model.** Use an ID actually supported upstream. Add `minimal`,
   `low`, `medium`, `high`, or `xhigh` reasoning only when needed.

7. **Keep `wire_api = responses`.** Codex no longer supports `chat`.
   Chat-only upstreams require OcHub gateway conversion.

8. **Review and switch.** Confirm the Provider ID, endpoint, model, and auth
   mode in the `config.toml` preview.

9. **Open a new Codex session.** Make a short request and verify request model,
   pricing model, and status in Usage.

</Steps>

## When to use a model provider

Prefer [model provider mode](/getting-started/relay) when:

- The upstream supports Chat Completions but not Responses.
- A Codex model alias must be rewritten to an upstream ID.
- Routing should choose among Anthropic, Chat, and Responses.
- You need gateway-level time to first token, total latency, and errors.
- Future upstream changes should not rewrite `config.toml` repeatedly.

Codex remote compaction requires an OpenAI Responses upstream. Ordinary
requests can convert to Chat, but remote compaction cannot use a Chat-only
upstream.

## Models and reasoning

The model field becomes the current Codex model. Reasoning effort works only
when the model and upstream support Responses reasoning parameters.

1. First verify the model with no effort set.
2. Try `medium`.
3. Compare latency and output before moving to `low`, `high`, or `xhigh`.
4. If the upstream rejects the parameter, clear it instead of changing the
   key and model at the same time.

Remote compaction is enabled by Codex only when the provider name is exactly
`OpenAI`. Leave it off unless a third party fully implements the Responses
compaction behavior.

## Advanced request options

| Field | Purpose | Example |
| --- | --- | --- |
| Disable response storage | Set `disable_response_storage = true` | ZDR or an upstream without storage |
| Query parameters | Append values to every request URL | Azure `api-version` |
| HTTP headers | Add custom request headers | Tenant, project, or route ID |

Complete a normal request first, then add one option at a time. Keep long-lived
secrets in the dedicated API-key field rather than ordinary custom headers.

## Official login

If Codex is already signed in:

1. Add or choose an Official login connection.
2. Switch and confirm the official endpoint behavior returns.
3. Restart Codex.
4. Make one request and verify that no third-party provider error remains.

Enable **Keep current OAuth for third parties** in Codex App settings
to preserve `auth.json` while using third-party model requests and make
switching back easy.

## Unified and migrated history

Two Codex settings have different purposes:

- **Migrate existing Codex sessions** imports official history during the next
  migration.
- **Unify Codex session history** places official and third-party sessions in
  one history location.

Before changing them, quit Codex, back up `~/.codex` or the custom directory,
change one option at a time, restart, and inspect the session count and date
range.

Under **Advanced tools → Codex history**:

- Check unified-history backup reports whether a restorable backup exists.
- Restore official-history backup may overwrite current official history, so
  make another directory backup first.

## MCP and skills

Codex supports OcHub-managed MCP and skills.

- Enable Codex on an MCP card and sync it into `config.toml`.
- Choose Codex when installing a skill or enable it on an installed card.
- A custom Codex directory changes both destinations; restart after syncing.
- OcHub tolerates legacy `[mcp.servers.*]` input during import and writes the
  current format.

## Common problems

| Symptom | Likely direction | Fix |
| --- | --- | --- |
| `chat` was removed | Wrong `wire_api` or Chat-only upstream | Use Responses or gateway conversion |
| Base URL returns 404 | Incorrect `/v1` level | Verify the final path is `/v1/responses` |
| Account remains but request gets 401 | OAuth is not the third-party key | Check mode and third-party API key |
| Remote compaction fails | Incomplete Responses support | Disable it or use a Responses upstream |
| Model did not change | An old Codex process is running | Restart and inspect the preview |
| Session count is wrong | History directory or unify setting changed | Verify the directory and backup |

For a Chat-only upstream, continue to
[Routing recipes](/advanced/routing-recipes). For combined login and routing,
remote compaction, Responses WebSocket, and provider history buckets, see
[Advanced Codex pitfalls](/codex/advanced).

## Real ChatGPT login with relay and context management

Starting with OcHub 0.5.16, station connections preserve real ChatGPT login and automatically bind the local gateway identity to the selected station.

1. Sign in to ChatGPT in Codex. The corresponding Codex source accepts Plus, Pro, and ProLite accounts for experimental context management.
2. Configure the third-party endpoint, API key, models, and routing under **Model providers**. Remote compaction requires Responses `/responses/compact` support; ordinary Responses support alone is insufficient.
3. Add a Codex connection sourced from that station and select **ChatGPT login + OcHub relay**.
4. Leave **Virtual ChatGPT login** off, enable **Context management**, save, and switch. Keep the third-party key in the upstream endpoint configuration.
5. Start a fresh Codex session. Verify a short request, then a long conversation or `/compact`, and inspect the routed model in usage logs.

One-click station application also selects this mode when a real account is already present. Activation enables the Codex backend and model catalog and binds the account to the station key identity. Saving an inactive connection does not change the active binding. The binding is gateway-wide: real-login sessions sharing this gateway use the most recently selected identity.

```toml
model_provider = "custom"
model = "your-model-id"

[model_providers.custom]
name = "OpenAI"
base_url = "http://127.0.0.1:4180/backend-api/codex"
wire_api = "responses"
requires_openai_auth = true

[features.context_management]
experimental_mode = true
```

Keep the real account in `auth.json`. Codex sends its account token to the local gateway; OcHub replaces Authorization with the upstream endpoint key. Third-party billing still applies.

### Eligibility and virtual login

The automatic activation path requires provider name `OpenAI`, a URL ending in `/backend-api/codex`, `requires_openai_auth = true`, and no `experimental_bearer_token`, `env_key`, independent `auth`, or `aws` credentials. **ChatGPT login + third-party API** writes a provider bearer token and fails this check. Successful activation enables Token Budget and the history/notes extension. Managed requirements can still disable Token Budget. Configure accurate model context windows and tool capabilities; enabling the flag does not establish long-conversation reliability for every upstream model.

Virtual login places an OcHub `rd-…` key in a local login file when no real account exists. It grants no ChatGPT subscription or official quota and cannot overwrite a real login. Station connections now respect this toggle.

### Manual gateway binding

Manual connections do not infer a station from an arbitrary URL. Create an enabled, route-bound gateway key, then use its record ID (not the `rd-…` secret):

```sh
ochcli gateway key list
ochcli gateway config set --codex-backend true --codex-models true --codex-oauth-key-id KEY_ID
```

To revoke real-login access:

```sh
ochcli gateway config set --clear-codex-oauth
```

This mode maps unverified, nonempty bearer tokens to a specific route identity; it does not verify ChatGPT account ownership. The gateway listens on loopback only. Missing bindings, disabled keys, and retired `rd-…` keys are rejected. `/v1` authentication is unaffected.

### Compact interface field reference

Forms retain labels, controls, state, and validation. Detailed explanations live here; use the documentation button in the editor toolbar.

| Field | Meaning |
| --- | --- |
| Provider ID | The `model_providers` key and Codex provider identity; keep it stable |
| Provider name | Internal Codex name; login-shaped OcHub relay uses `OpenAI` |
| Base URL | Usually `/v1` for direct APIs; local `/backend-api/codex` for login relay |
| API key | Upstream credential for direct API modes; an OcHub `rd-…` key for virtual login |
| Remote compaction | Requires a compatible Responses compaction upstream |
| Context management | Writes `features.context_management.experimental_mode`; eligibility checks apply |
| Token Budget | Explicit client budget activation, subject to model defaults and managed requirements |
| Reminder threshold | Remaining tokens before the state-preservation reminder; blank uses client defaults |
| History notes extension | Enables history/notes tools for context management |
| Responses WebSocket | Must match upstream capability; station connections inherit it |
| Disable response storage | Automatically enabled for station connections; OcHub has no Responses store |
| Query parameters and headers | Upstream-specific metadata; station connections are managed by OcHub |

| Symptom | Check |
| --- | --- |
| 401 | Enabled route-bound key identity; manual connections need KEY_ID |
| 404 | Backend activation, endpoint path, and upstream compaction support |
| Context feature absent | Plan, provider name, URL suffix, independent credentials, managed requirements |
| Only compaction fails | `/responses/compact` support; Chat-only channels cannot compact |
| Virtual login rejected | Keep the real account and turn virtual login off |
