OcHub のコストはリクエストのトークン、モデル価格、倍率から計算するローカル推定値で、
プロバイダーの請求書ではありません。OcHub 独自の内蔵価格表は維持していません。
モデル ID や課金元が一致しないと、成功したリクエストでもコストが 0 になります。

## コストを決めるもの

1 リクエストに 3 つのモデル名がある場合があります。

| 名前 | 意味 |
| --- | --- |
| リクエストモデル | クライアントが送ったモデルまたはエイリアス |
| モデル | 上流が返した、または実際に処理したモデル |
| 課金モデル | OcHub が価格を検索するモデル |

ゲートウェイ変換ではすべて異なることがあります。クライアントが
`claude-sonnet-current`、上流が `anthropic/claude-sonnet-4-6` の場合、実際の請求に
合う ID を課金モデルにします。

価格表には米ドルで 100 万トークンあたりの 4 項目を保存します。

- 入力
- 出力
- キャッシュ読み取り
- キャッシュ書き込み（内部ではキャッシュ作成）

4 つの基礎コストを加算して倍率を適用します。キャッシュの意味もアプリごとに処理します。
Claude 型の入力は通常新規入力ですが、Codex / Responses の入力にはキャッシュ読み取りが
含まれるため、通常入力価格の前に差し引きます。

## 価格の出所と同期

アプリには、CI が LiteLLM の公式データから絞り込み、検証して特定リビジョンへ固定した
オフライン料金カタログが同梱されます。初回起動にネットワークは不要で、OcHub が別の価格を
手作業で管理するものでもありません。バックグラウンドの条件付き確認は 1 日最大 1 回です。
**使用量 → モデル価格設定**の「今すぐ同期」から直ちに確認することもできます。失敗しても
最後の有効なカタログを使い続けます。

価格は次の順序と条件で解決します。

1. ユーザーが保存した手動上書きが常に優先され、同期で変更または削除されません。
2. カタログは完全な Provider / リージョン付きキーを優先し、次に直接のモデルキーを照合します。
3. 同じエイリアスの全候補で 4 価格が一致する場合だけ自動採用します。差があれば推測しません。
4. 実際にキャッシュトークンがあり、対応するキャッシュ単価が欠けている場合、`0` とみなしません。

トークンはあるものの確実に価格を決められないモデルは、繰り返しダイアログを出さず 1 つの
不足料金通知へまとめます。同期または手動上書きの追加後、トークンがありコストが 0 の履歴を
補完します。既存の非ゼロコストは一括で書き換えません。

## 正しいモデル ID を探す

1. 実リクエストを送ります。
2. **使用量 → リクエストログ**で開きます。
3. リクエストモデル、モデル、課金モデルを記録します。
4. プロバイダーの価格表と比較します。
5. 実際の請求モデルを表す ID を追加します。

課金モデルがカスタムエイリアスなら、レスポンスモデル課金へ変える、エイリアス価格を作る、
ルートマッピングを安定させる方法があります。価格表の ID と課金モデルを一致させるのが
最も確実です。

## 手動価格上書きを追加する

<Steps>

1. **使用量でモデル価格設定を展開し、手動価格上書き表を開きます。**

2. **モデル ID を入力します。** 課金モデルと一致させます。大文字小文字、プロバイダー接頭辞、
   バージョン接尾辞が影響する場合があります。

3. **表示名を入力します。** 読みやすさだけに作用し、ルーティングには影響しません。

4. **4 つの価格を入力します。** 単位は米ドル／100 万トークンです。プロバイダーの規則上
   キャッシュ料金がない場合は `0` を使います。

5. **保存します。** 非負の数値が必要で、同じ ID は更新されます。

6. **更新して個別リクエストを確認します。** 課金モデル、項目別、総コストを確認します。

</Steps>

手動上書きの保存後、OcHub はトークンがあり総コストが 0 の同モデル履歴を補完しようとします。
すでに非ゼロの履歴をすべて再計算するわけではないため、価格変更前後で基準が分かれる場合があります。

<Aside type="note" title="価格変更はプロバイダー請求を変えません">

補完は OcHub のローカル使用量データベースだけを変更します。請求、残高、実際の課金には
影響しません。

</Aside>

## リクエストモデルとレスポンスモデル

Claude と Codex にはデフォルトの課金モデル元があります。

| 選択 | 適した場合 | リスク |
| --- | --- | --- |
| レスポンスモデル | 上流が変換後の実モデルを返す | 空またはエイリアスを返す上流 |
| リクエストモデル | クライアント ID が安定し価格表と一致 | ルーティング後に誤価格 |

直接接続とルーティング済みの両方でモデル名を比較し、実価格へ安定して一致する方を保存します。
新しいリクエストの課金モデルで確認してください。

Claude Desktop は Claude のデフォルト倍率と課金元を継承します。

## コスト倍率

既定 `1` は価格を変更しません。

| 精算ルール | 倍率 |
| --- | --- |
| 公開価格と同じ | `1` |
| 20% 上乗せ | `1.2` |
| 20% 割引 | `0.8` |
| トークンだけ記録し総コストへ含めない | `0` |

倍率は入力、出力、キャッシュの基礎コストを加算した後に適用され、トークン数は変えません。
モデルごとに上乗せ率が違う場合は、精算後の個別価格を入力し倍率 `1` を使います。

## 1 リクエストを手計算する

| 項目 | トークン | 100 万あたり | 基礎コスト |
| --- | ---: | ---: | ---: |
| 新規入力 | 10,000 | $3.00 | $0.03000 |
| 出力 | 2,000 | $15.00 | $0.03000 |
| キャッシュ読み取り | 20,000 | $0.30 | $0.00600 |
| キャッシュ書き込み | 5,000 | $3.75 | $0.01875 |

基礎合計は `$0.08475`。倍率 `1.2` では：

```text
$0.08475 × 1.2 = $0.10170
```

ページ全体の「実トークン」ではなく、1 件の詳細値を使います。Codex / Responses の
キャッシュ意味は OcHub がすでに正規化しています。

## プロバイダー請求と照合する

1. 同じ期間とタイムゾーンを使います。
2. 1 プロバイダーへ絞ります。
3. 失敗や再試行を含む件数を比較します。
4. 課金モデルを確認します。
5. システムプロンプト、ツール、推論トークンの扱いを確認します。
6. 入力とキャッシュの意味を確認します。
7. 倍率、割引、為替を確認します。
8. 日次合計の前に 1 リクエストを照合します。

アカウントプラン、段階価格、バッチ割引、リージョン、最低料金は 1 つの価格と倍率で正確に
表せない場合があります。OcHub はリクエスト単位の推定、請求書は精算記録として扱います。

## データソースの制限

| データソース | 通常ある項目 | 欠ける場合がある項目 |
| --- | --- | --- |
| モデルプロバイダー経由のリクエスト | ID、状態、モデル、トークン、レイテンシー | 上流が返さない項目 |
| CLI セッション | モデル、一部トークン、時刻 | ゲートウェイ状態、最初のトークン |
| 旧ローカルリクエスト | 履歴トークン、コスト | 現在の課金モデル意味 |
| 同期セッション | 元ファイルの項目 | プロバイダー、キャッシュ内訳 |

モデルまたはトークンがなければ、信頼できるコストは補完できません。

## よくある問題

| 症状 | 確認 | 対処 |
| --- | --- | --- |
| トークンあり、コスト 0 | 不足料金通知、課金モデル、キャッシュ価格 | 同期または正確な ID の手動上書き |
| 新規は正しく旧履歴が違う | 旧履歴がすでに非ゼロ | 変更時刻を境界にする |
| キャッシュコストが高い | 入力と読み取りの重複 | アプリと上流の意味を確認 |
| エイリアス価格になる | リクエストモデル課金 | レスポンスへ変更またはエイリアス価格 |
| コストが急変 | 倍率、接尾辞、価格更新 | 課金モデルと倍率を比較 |
| 請求と少し違う | 丸め、時差、失敗、プラン | 個別リクエストから照合 |
| 保存できない | 表示名空、負数、不正値 | 名前と非負小数を入力 |

日常の絞り込みは[セッションと使用量](/ja/guides/sessions-usage)を参照してください。
